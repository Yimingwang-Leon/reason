## 攻击面 2:天花板 89.94%(1708/1899)—— 部分证伪(口径自相矛盾)

**数字来源复算确认:** `rl/recon_data.md:39` 表 1.3。构成 = bit 297/320 + cipher 315/315 + gravity 319/319 + numeral 315/315 + unit 319/319 + eq 117/146 + crypt 26/165 = 1708/1899 = 89.94%(我复算 0.8994,与诊断书一致)。`1899 = LB 镜像规模`,各类题数 = train 真权 × 1899。

**致命点:健康类(cipher/gravity/numeral/unit)按 100% oracle 算入。**
- 健康类合计 1268 题,占天花板的 **66.8%(占整个 1899)/ 74.2%(占 1708 个 OK 题)**。
- 这是 **holdout oracle 天花板,不是 LB 天花板**。`1708/1899` 标注本身写的是 "LB 上限 = 0.899 × R",即它已经是把健康类当 100% 的 oracle 数。

**诊断书内部矛盾(本审查新发现):**
- §1.2 归因表为了填 2pp 残差,明确写"健康类 100%→LB 96.1%(−3.9pp)解释 run-012;或 →97.6%(−2.4pp)解释 run-011"。
- 但 §0 / §1.2 末 / §4 又用 89.94%(隐含健康类 = 100%)说"run-011 的 0.85 已是 98% 兑现 / 剩余空间在 oracle"。
- **同一文档对健康类 LB 取了两个互斥的值。** 若用归因里的自洽口径重算天花板:
  | 健康类 LB | 真天花板 |
  |---|---|
  | 100%(诊断书 §0 口径) | 89.94% |
  | 97.6%(诊断书 §1.2 run-011 自洽口径) | **88.34%** |
  | 96.1%(诊断书 §1.2 run-012 自洽口径) | **87.34%** |
- Wilson 95% 下界(健康类 holdout 440/440 全对 → 真 LB 下界 0.991)给天花板下界 = **89.38%**;但这只约束"现分布",对 LB 抽更难变体无能为力,真实更接近自洽口径 87–88%。

**0.87 是否数学上可达?**
- 即使取最悲观自洽口径(健康类 96.1% → 天花板 87.34%),**0.87 仍在天花板之内**,数学上不是不可达。
- 但"距天花板 89.94% 还有 5pp 空间、执行已榨干"的乐观框架被自身矛盾削弱:自洽口径下真天花板离 0.87 只剩 0.3–1.3pp,几乎贴脸。
- 到 0.87 需非健康类(bit+eq+crypt 共 631 题)答对率:健康类 100% 时 60.9%,健康类 97.6% 时 65.7%,健康类 96.1% 时 68.7%——而现状非健康类 oracle 远低于此(crypt 15.8%),**且这是 oracle 不是 LB**。

## 攻击面 3:bit 110/110 是否偷看 holdout / 五轮封顶矛盾 —— 关键反案

### 3a. bit 110/110 没有 eq 式 holdout 偷看(确认 bit_prior 干净)
- `rl/bit_prior.py:396` 学先验前剔除 holdout id(`bit = bit[~bit['id'].isin(set(hbit['id']))]`),无泄漏。
- 覆盖率(truth ∈ 候选集)只用 examples 枚举,不用 truth 选族;裁决 `decide()` 不读 truth。
- 交叉验证:train(去 holdout)覆盖 **1489/1492 = 99.8%**,holdout **110/110 = 100%**,train 5-fold prior **1475/1492 = 98.9%**(我跑 `bit_prior.py` 全复现)。train 与 holdout 覆盖几乎一致 → 规则族**不是 holdout-specific**,与 eq(`_MODE_ORDER` 硬编进 production solver 直接在 holdout 调)有**本质区别**。
- **结论:bit 110/110 这个 oracle 数本身是干净的,不是第二个 eq 式过拟合。** 这一点诊断书 §2④判断正确。

### 3b. 但"+19≈+2.5pp 是别人 0.87 来源 / 真矿在 bit"被五轮实训直接证伪(本审查最重发现)
`data/probes/r3*_flips.json` 是 `bit_port_report.md` 把 `bit_prior.py` 扩展族+先验**移植进 production solver、重生成语料、实训后**的 bit110 判卷结果(基线 run-011 = **94/110**,我从 `r011_bit110_baseline.jsonl` 复算确认 94):

| 轮 | up | down | 净 | bit110 绝对值 |
|---|---|---|---|---|
| r3  | 0 | 43 | **−43** | 51 |
| r3b | 2 | 8  | **−6**  | 88 |
| r3c | 4 | 6  | **−2**  | 92 |
| r3d | 3 | 43 | **−40** | 54 |
| r3e | 4 | 4  | **0**   | 94 |

- **五轮实训,净增从未 > 0;最好一轮(r3e)= 94,精确打平基线,零兑现。** 离线宣称的 +19(110/110 vs 91 旧基线,或 +16 vs 94 新基线)在实训里一次都没出现过哪怕 +1。
- 诊断书 §4.1 用"此前死磕的是错误子问题(窄族内部消歧),换对的扩展族就能 +19"来解释五轮封顶——**但 r3–r3e 恰恰是用对的扩展族(bit_prior.py 1:1 移植)重训仍封顶**,这把"挖错坑"的辩解也推翻了:不是族不对,是**oracle→LB 的兑现机制失效**(模型学不进新族 trace,长格式/扫描结构崩,见 bit_port_report v1 94→51、v2 94→88 验尸)。
- 诊断书在 §3/§4.2 标注了"兑现风险大",但引用的反例是 bit-EV +114 oracle 0/30 和 run-006/7/8 R 崩——**完全没引用 r3–r3e 这五轮针对"扩展族+先验"本身、且早于 GAP_DIAGNOSIS 撰写日已落盘的实测**。这是诊断书的选择性遗漏:最直接的反证摆在 `data/probes/` 里没用。

### 3c. "19 道丢分 16 道族外无歧义"复算
- `bit_prior_full.log` + `bit_prior.py` 输出:holdout 修复 19 题、打破 0、mincost 裁决都能 109/110,确认"歧义是伪问题、族覆盖才是瓶颈"在 **oracle 层成立**。
- 但 oracle 层成立 ≠ LB 层可兑现。RETHINK.md §1.6 另一口径(run-011 真实采样)说 bit 23 失败里 18 道 cls=none(连候选都生不出)、仅 1 道 truth 是 plurality——与 dig_bit 的"16/19 族外无歧义"是**同一现象的两种表述**(族外 = 模型生不出候选),都指向"模型执行层够不到扩展族",而非"族选对了就能赢"。
